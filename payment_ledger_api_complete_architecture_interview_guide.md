# Comprehensive Guide: High-Concurrency Payment Ledger & AI Auditor

## 1. System Architecture & Core Philosophy
This project simulates the backend engine of a digital wallet or payment processor (like Visa, Stripe, or PayPal). While the Redis clone proved you understand *speed and memory*, this project proves you understand **data integrity and consistency**.

In financial systems, dropping a request or running slightly slow is acceptable; **double-charging a user or creating money out of thin air is a catastrophic failure.**

### The Core Paradigm: Double-Entry Ledger
*   **The Rule:** Money is never simply "updated." It is moved. Every transaction consists of at least two immutable entries: a debit from Account A and a credit to Account B.
*   **The Architecture:** Built using Python (FastAPI for asynchronous API handling) and PostgreSQL (for strict relational data guarantees).

## 2. Deep Dive: Core Concepts (The Interview Differentiators)

### A. Race Conditions & Row-Level Locking
*   **The Threat:** Imagine Account A has $100. Two separate API requests arrive at the *exact same millisecond* to transfer $100 out of Account A. Both requests check the balance, see $100, and proceed. The account ends up at -$100, breaking business logic.
*   **The Fix (Pessimistic Locking):** You will use PostgreSQL's `SELECT ... FOR UPDATE` via SQLAlchemy.
*   **How it Works:** When Request 1 starts processing, it locks the database row for Account A. Request 2 must wait in line until Request 1 completely finishes its transaction. Request 2 then reads the *new* balance ($0) and gets rejected due to insufficient funds.

### B. Idempotency (Preventing Duplicate Charges)
*   **The Threat:** A user's internet lags, so they click the "Pay" button three times in a row. The frontend sends three identical transfer requests.
*   **The Fix:** Every incoming API request must include a unique `Idempotency-Key` in the HTTP header (usually a UUID generated by the frontend).
*   **How it Works:** 
    1. The backend receives the request and checks the `idempotency_keys` database table.
    2. If the key doesn't exist, it processes the payment, saves the exact JSON response to the table, and returns it.
    3. If the key *does* exist, the backend skips the payment logic entirely and simply returns the saved JSON response. The user gets charged exactly once.

### C. Pragmatic AI Integration (The "Smart Auditor")
Instead of building a complex, flaky RAG system, you will use GenAI to solve a real-world banking problem: categorizing unstructured transaction data.
*   **The Feature:** When a user submits a payment with an unstructured memo (e.g., "Uber ride home from airport" or "Starbucks coffee large"), a background worker triggers an LLM API (like Google Gemini or OpenAI).
*   **The Execution:** The LLM is given a strict system prompt and a Pydantic schema to extract structured JSON (e.g., `{"category": "TRANSPORT", "confidence": 0.95}`).
*   **The Fallback:** If the AI API fails, times out, or hallucinates bad JSON, the system catches the error and assigns a default `"UNCATEGORIZED"` tag, ensuring the core payment flow never breaks.

## 3. Database Schema Design

1.  **`accounts` table:**
    *   `id` (UUID, Primary Key)
    *   `balance` (Decimal/Numeric - never use Float for money!)
    *   `currency` (String)
2.  **`transactions` table:**
    *   `id` (UUID, Primary Key)
    *   `from_account_id` (UUID, Foreign Key)
    *   `to_account_id` (UUID, Foreign Key)
    *   `amount` (Decimal)
    *   `status` (Enum: PENDING, COMPLETED, FAILED)
    *   `ai_category` (String, populated later by the AI worker)
3.  **`idempotency_keys` table:**
    *   `key` (UUID, Primary Key)
    *   `response_body` (JSON)
    *   `created_at` (Timestamp)

## 5. Interview Defense: Crucial Questions to Prepare

*   **Q: Why use `Decimal` instead of `Float` for balances?**
    *   *A:* Floating-point math introduces precision errors due to how computers represent fractions in binary (e.g., 0.1 + 0.2 = 0.30000000000000004). In financial systems, `Decimal` (or storing everything as integers representing cents) guarantees exact precision.
*   **Q: What is a deadlock and how did you prevent it?**
    *   *A:* A deadlock happens if Transaction A locks Account 1 and tries to lock Account 2, while Transaction B locks Account 2 and tries to lock Account 1. I prevented this by always sorting the account IDs in memory before requesting the DB locks (e.g., always lock the smaller UUID first), ensuring all concurrent transactions lock rows in the exact same order.
*   **Q: Why put the AI call in a background task instead of the main API flow?**
    *   *A:* AI APIs have unpredictable latency (anywhere from 300ms to 5 seconds). Tying that to a core payment flow would frustrate the user and hold open valuable database connections. Moving it to an async background worker ensures the payment completes in ~50ms, and the AI enrichment happens eventually.
